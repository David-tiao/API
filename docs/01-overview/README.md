# 01｜零基础精简篇：读懂 API Extractor

> 不要求会编程，不需要安装软件。本篇不含运行命令；想动手请转到 [03 操作篇](../03-operations/README.md)。想深入代码、公式和设计历史请转到 [02 专业篇](../02-technical/README.md)。

## 1. 这个项目解决什么问题？

网上商城里，你搜索“苹果”，页面显示商品和价格。显示内容的是前端，查找商品数据的是后端。两者之间有一套约定：前端向后端发送请求，后端返回数据。这套约定中的一个交流入口称为 API（应用程序接口）。

API Extractor 的任务不是购物，也不是破解网站，而是在**明确获得授权的网站**上自动寻找这种交流入口，整理出它们的地址、请求方式、部分参数，并留下可以核对的证据。

像整理一栋楼的门牌：既可以看建筑图纸，也可以观察哪些门确实被打开过。但不能因为找到一些门，就宣称已经发现全楼所有门。

## 2. 基础概念：先认识网页，再认识提取器

| 名词 | 通俗解释 |
|---|---|
| 前端 / 后端 | 前端是你看到、操作的网页；后端是服务器上的数据处理程序。 |
| 浏览器 / 服务器 | 浏览器负责展示和运行网页，服务器提供网页、数据或其他服务。 |
| API / Endpoint（接口端点） | API 是程序之间的交流约定；端点是其中一个具体入口，通常由请求方法和路径区分。 |
| URL / Host / Path | URL 是完整地址；Host 是主机名，像楼的地址；Path 是资源路径，像房间门牌。 |
| HTTP / HTTPS | 浏览器与服务器交换信息的规则；HTTPS 在 HTTP 基础上加密传输。 |
| 请求 / 响应 | 请求是向服务器提出要求，响应是服务器返回的结果。 |
| GET / POST / PUT / PATCH / DELETE | 请求方法，常分别用于读取、提交、整体替换、部分修改、删除。实际语义由服务器决定，GET 也不一定没有副作用。 |
| 参数 / Header（请求头） / Body（请求体） | 参数是附带的问题或条件；请求头是附加说明；请求体是提交的内容。 |
| 状态码 | 服务器回应的数字，例如 200 常表示成功，401 常表示未认证，403 表示禁止访问，404 表示未找到。 |
| Cookie / Token / API Key | 用来维持会话或证明身份的凭据；像临时通行证，不应该公开。 |
| Bearer / 签名 | Bearer 是一种携带令牌的认证方式；签名是用于验证请求身份或完整性的计算结果。发现签名字段不等于懂得计算签名。 |
| HTML / CSS / JavaScript | HTML 是网页骨架，CSS 是外观，JavaScript 是网页运行时的逻辑。 |
| JSON / JSONL | JSON 是结构化数据格式；JSONL 是每一行独立的 JSON，适合持续记录日志。 |
| Python / Node.js | Python 是主程序使用的语言；Node.js 是运行 JavaScript 工具的环境。 |
| Fetch / XHR / axios | 网页 JavaScript 与服务器通信的常见方式；axios 是封装网络请求的库。 |

## 3. 项目为什么要采用两种分析方法？

**静态分析**像阅读图纸：不必执行每条接口请求，就从网页和 JavaScript 中寻找调用声明。AST（抽象语法树）是把代码整理成有结构的树，帮助程序理解哪些部分是函数、参数和字符串；Regex（正则表达式）则像按文字模式搜寻。Babel 是这里使用的 JavaScript 语法解析工具。它们能提供线索，但不证明接口真的被请求过。

**动态分析**像现场观察：让 Chromium（浏览器）实际运行网页，借助 Playwright（控制浏览器的程序库）记录网页发出的请求。这样可以看见实际访问，但看不到没有执行的业务路径。

两者结合的好处是既能获得源码中的线索，也能核对实际网络行为。代价是仍会漏掉未走到的页面、按钮或特殊认证流程。

### 现代网页还有哪些特别情况？

| 名词 | 通俗解释 |
|---|---|
| SSR（服务端渲染） | 服务器先把网页的主要结构生成好，浏览器收到后展示。 |
| SPA（单页应用） | 网页不用每次都重新加载整个页面，就能切换内容。前端路由是这种内部页面切换的地址规则。 |
| Hash 路由 | 使用地址中井号后的部分区分前端页面，通常由浏览器中的程序处理。 |
| 懒加载 / Chunk | 等真正需要某个功能时才加载的一小块代码。没有走到该功能就可能看不到它。 |
| REST | 常见的接口设计风格，用资源路径和请求方法组织操作；不是所有 HTTP 接口都符合 REST。 |
| GraphQL | 客户端可以描述想取得的字段，一般多个操作共用一个入口。 |
| WebSocket | 浏览器与服务器建立持续的双向通道，像通着的电话。 |
| SSE | 服务器持续向浏览器单向发送事件，像持续接收通知。 |
| Socket.IO | 一种实时通信方案，可用 HTTP 轮询（反复请求）或 WebSocket；连接记录不一定是业务接口。 |

## 4. 把架构理解成一条流水线

架构就是把复杂任务拆成不同职责，再规定信息怎样流动。本项目不是让一个文件做所有工作：

| 顺序 | 流水线角色 | 它负责什么 |
|---|---|---|
| 1 | 接待与调度 | 读入目标地址、配置、输出位置和时间预算，安排后续步骤。 |
| 2 | 门卫与交通管理 | Scope（授权范围）限制允许访问的主机；限流控制单位时间请求量，并发控制同时处理的请求数。 |
| 3 | 资料收集员 | 获取网页、已有链接和部分脚本。 |
| 4 | 图纸研究员 | 分析代码中可能出现的接口。 |
| 5 | 现场观察员 | 浏览器访问页面，记录真正发出的请求，并收集实际加载的新脚本。 |
| 6 | 整理员 | 将不同来源的记录统一为候选；归一化把不同编号的同类资源路径整理成一个模板，去重避免重复登记。 |
| 7 | 审核员 | 对照日志和证据，检查哪些候选真的发生过请求。 |
| 8 | 交付员 | 按 JSON Schema（规定数据字段和类型的格式规则）生成结果。 |

**最重要的规则：** 图纸上有门，不代表现场观察到开门；仅从源码发现的接口只能作为线索。

## 5. 代码放在哪里？只记住最关键的文件

| 路径 | 作用 |
|---|---|
| `api_extractor/` | 核心程序目录。 |
| `api_extractor/cli.py` | 命令行入口；CLI 是通过终端参数与程序交互的方式。 |
| `api_extractor/pipeline.py` | 总调度，决定工作顺序。 |
| `api_extractor/config.py` / `scope.py` / `request_control.py` | 分别读取配置、检查范围、控制请求量。 |
| `api_extractor/crawler.py` | 收集网页和脚本。 |
| `api_extractor/static_analysis.py` / `dynamic_analysis.py` | 分别做源码分析和浏览器观察。 |
| `api_extractor/candidates.py` / `normalization.py` | 统一来源、合并相似记录、推断部分字段。 |
| `api_extractor/evidence.py` / `output.py` | 核对证据和输出报告。 |
| `tools/` | JavaScript 解析辅助程序。 |
| `tests/` | 自动检查程序行为的测试；pytest 是执行 Python 测试的工具。 |
| `scripts/` | 安装、启动、诊断和验收所用脚本。 |
| `examples/` | 配置和结果的示例。 |
| `docs/` | 项目说明、技术设计与运行操作。 |
| `.github/workflows/` | GitHub Actions 的自动测试配置。CI（持续集成）指代码变化后自动检查。 |
| `Dockerfile` | Docker 容器镜像的制作说明。镜像像装好程序和依赖的模板；容器是使用模板运行的隔离环境。 |
| `requirements.txt` / `package.json` | Python / Node.js 所需第三方软件包的清单。 |

Git 是记录代码历史的工具；GitHub 是托管代码的服务。main 是主要代码分支；PR（Pull Request）是提出合并改动的记录。详细源码关系请读 [专业架构篇](../02-technical/01-ARCHITECTURE.md)。

## 6. 最终会得到什么？

| 文件 | 怎样理解 |
|---|---|
| `result.json` | 正式清单。通过请求证据检查的接口或协议传输记录，可能包含需要认证的请求，不保证全部成功或可重放。 |
| `static_candidates.json` | 从源码发现且尚无真实请求证据的候选线索。 |
| `tool.log` | 程序做了什么的流水账，包括每次运行的状态。 |
| `evidence/` | 证据目录；HAR 是浏览器网络记录的格式，这里保存请求摘要，以及部分网页和 JS。 |

如果运行状态是 completed，表示本轮流程正常结束，不表示已经探索所有页面。partial_browser_failure 表示浏览器阶段部分失败；incomplete_budget 表示时间预算耗尽。输出格式正确也可能只有部分结果。

## 7. 能做到什么程度？

已完成：267 项 Python 测试和 10 次实际 Chromium 合成测试；自行部署的 Juice Shop 两轮均得到 9 条有请求证据的记录，其中 3 条是 Socket.IO 传输，两轮集合相同。

**不能保证：** 任意站点所有 API 都找到、任意登录都成功、还原任意签名算法、理解全部实时消息、通过官方隐藏考核或全部系统级安全审计。工具只在授权范围使用，不用于绕过认证或操作未知危险功能。

召回率指真正接口找到了多少，精确率指报告的接口中有多少是真的；没有权威的真实接口清单（真值），就无法计算可靠的分数。两轮一致不等于两轮都找全。

更多见 [能力与限制原始说明](../CAPABILITIES_AND_LIMITS.md)；实测证据见 [专业版本简史](../02-technical/03-VERSION_HISTORY.md)。
