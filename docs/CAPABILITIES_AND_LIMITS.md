# API Extractor 能做到什么、做不到什么？——能力范围与验证边界

> **适用版本：** 2026-11-23 的工程收官基线（软件版本 `0.1.0`）。本页基于当时已合入 `main` 的源码和已完成的 GitHub Actions / 自建练习站验收记录。后续代码变化请结合当前源代码、`README.md` 和 CI 重新核对。
>
> **一句话定位：** 它是一款针对**明确授权的 Web 站点**，以发现前端 API、保留请求证据为目标的**有界自动化提取工具**。它不是任意网站的完整 API 地图、漏洞利用工具、通用认证绕过器，也不是正式考核得分保证书。

## 1. 先看结论：能力分级

| 分级 | 说明 | 该怎么理解 |
|---|---|---|
| **A：已有端到端证据** | 在仓库的合成站点或自行部署的 Juice Shop 上实际运行并检查了输出 | **这些具体场景**已验证，不等于所有外部网站 |
| **B：代码支持，效果依赖站点** | 已有对应实现和部分测试，但对陌生站点的覆盖率不确定 | 可以尝试；不能承诺一定发现/重放 |
| **C：目前做不到或未充分验证** | 没有完整实现、没有必要权限/真值，或尚未进行系统级审计 | 不能对外宣传为已支持或已达标 |

### 一张表看懂“能做到什么程度”

| 能力 | 程度 | 具体能做到 | 做不到或不能保证 |
|---|---|---|---|
| **网页基础采集** | **A / B** | 在授权范围内获取 HTML、部分 JS/CSS、链接和表单；限制抓取量 | 不能遍历全站所有隐藏页面和无限深度的资源 |
| **JavaScript 静态 API 线索** | **A / B** | Babel AST + 正则兜底，寻找 `fetch`、axios、XHR、WebSocket 等调用与相关路径 | 变量运行时拼装、强混淆、加密或运行环境依赖可能导致漏报；源码声明不等于真实请求 |
| **浏览器真实请求观察** | **A** | Chromium / Playwright 观察页面实际触发的 Fetch/XHR 等请求，记录 HAR 与日志 | 不会自动覆盖必须通过未知业务交互才会触发的所有接口 |
| **SPA / 前端路由** | **A / B** | 识别部分同站 `#/...`、Angular `routerLink` 路由，按限制导航；专用合成场景已验证 | 不能自动操作所有复杂前端路由、虚拟列表、权限菜单或自定义组件 |
| **懒加载 JS chunk** | **A / B** | 可分析浏览器**已经实际下载**的 JS chunk；单个 2 MiB、总量 8 MiB、最多 32 个 | 不会神奇发现尚未加载的所有 chunk，也不把未调用的接口声明算进正式请求报告 |
| **基础账号密码登录** | **A / B** | 常见用户名/密码表单可尽力填写；合成站已验证 Cookie 登录、POST→303→GET | 不能保证 MFA、验证码、SSO、二维码、OAuth 专属流程、多步骤业务登录 |
| **REST 风格接口整理** | **A / B** | 输出方法、Host、路径、部分参数/响应字段/鉴权类型；归一化和去重 | 不保证业务语义、字段完整性或参数类型判断总是正确 |
| **GraphQL** | **B** | 识别部分 GraphQL 入口、请求及操作/变量线索 | 不能推导完整 Schema、所有 resolver、复杂订阅或所有业务对象关系 |
| **WebSocket** | **A / B** | 在浏览器观察到的连接可记录握手线索与相关证据 | 不保证解读二进制帧、私有协议、所有频道或完整订阅语义 |
| **Socket.IO** | **A（传输分类）** | 自建 Juice Shop 两轮均把观察到的轮询 GET、POST 与 WS 传输标注为**传输层记录** | 不等于发现全部实时业务事件；更不能把三个传输请求称为三个 REST 业务 API |
| **SSE 事件流** | **A（合成场景） / B（泛化）** | 可从授权的 SSE 请求中有界采样一个完整真实数据事件；默认最多 32 KiB、5 秒 | 不是长期不断线的全量事件订阅器；不保证多条事件、无限时长或认证复杂的流 |
| **签名/认证分析** | **B** | 可以观察或标注 Cookie、Bearer、API Key、疑似签名字段 | **不能通用逆向签名算法**、重造任意签名、伪造凭据或绕过认证 |
| **证据核验** | **A** | 对正式结果的 HAR、JSONL 日志和请求索引/状态进行一致性审核；有 Schema 校验 | HAR 只证明**本轮记录到了对应请求**，不证明全站接口已找齐或业务逻辑已理解 |
| **本地显式 GET 验证** | **B（仅可选）** | 操作者提前列出最多 5 个明确授权、无副作用且出现在静态候选中的准确 GET URL 时，可尝试得到真实响应证据 | 默认**不会主动枚举和验证所有静态接口**；GET 本身也未必只读，不能用它针对隐藏考场手工适配 |
| **访问边界/资源控制** | **A（部分合成） / C（正式审计）** | `ScopeGuard`、逐跳重定向检查、共享限流；合成场景拒绝未授权访问 | **正式代理、DNS、文件系统审计尚未等价验收**；不能声称系统级零越界风险 |
| **稳定运行与交付** | **A（已测环境） / B（其他环境）** | CLI、Docker、JSON Schema、日志和自动回归链路；能保留部分合法结果并标记状态 | 不能保证任何机器/网络都能成功安装、所有页面不超时、镜像任意环境都是同样大小与构建速度 |

上表中的 **A** 不是“功能 100% 完美”，而是“有对应可复核的测试场景”；**B** 表示覆盖深度随网站变化。具体文件入口见 [项目架构](architecture.md)、[源码目录说明](PROJECT_STRUCTURE.md)。

## 2. 具体能帮用户完成哪些任务？

### 场景一：想知道自己的网页实际请求了哪些 API

**适合。** 例如有一个自己部署的练习商城，输入授权首页地址后，工具会尝试采集资源、打开有限数量的页面、观察真正发出的网络请求，并输出有证据的接口。对于实际未触发的接口，它可能提供静态线索，但不会冒充为已发生请求。

你得到的典型文件：

```text
out/
├── result.json             HAR / 本轮日志可证实的接口与传输记录
├── static_candidates.json  JS / HTML 中发现但尚未实测的接口线索
├── tool.log                 运行过程和最终 run_status
└── evidence/
    ├── dynamic.har          真实浏览器请求摘要
    ├── probe.har            仅在显式授权 GET 验证时可能有记录
    ├── js/                  保存的 JavaScript
    └── pages/               保存的网页
```

**合理预期：** “获得一份有证据的**已观测请求清单**”；不应预期“知道该网站所有隐藏接口”。

### 场景二：想检查自己的 SPA / 懒加载页面里可能还有什么接口

**部分适合。** 工具会在有限预算内探索已有链接和安全的 Hash 路由。浏览器在这些路由后加载的 JS chunk，也可以做 AST/正则分析；源码里**只是声明**的 API 被记录为静态候选，而不是直接当成真实业务 API。

**合理预期：** “发现一些尚未执行的调用线索，供人工继续调查”；不应预期“自动遍历所有前端功能”。

### 场景三：想做开发回归、给项目演示

**适合。** 可用本仓库合成站点、`pytest`、GitHub Actions / Docker 验证基本功能；可在自行部署的授权 Juice Shop 容器上复现双轮检查，并从真实日志读取结果。

**合理预期：** “证明当前改动没有破坏既有测试用例”；不应预期“自动通过未知环境的官方考核”。

### 场景四：输入一个任意大型网站，就让工具把它全部 API 逆向出来

**不适合保证这个目标。** 复杂网站涉及不同用户权限、未观察到的业务分支、CDN、签名、验证码、动态加载、多阶段认证、反自动化和自定义通信协议。工具有边界保护，不会为追求覆盖率无限访问或尝试危险操作。

**合理预期：** 只能拿到本次授权范围、导航路径、时间预算和已观测流量所允许的一部分发现。

## 3. 这个工具刻意**不做**什么？

这些是能力与安全设计边界，并不是“忘记开发”：

1. **不突破授权边界。** 它不提供绕过授权、登录破解、验证码破解、权限提升的通用功能。
2. **不以暴力枚举代替证据。** 不默认重放 JS 中提到的任意 POST、DELETE、支付/退出登录等未知操作；从 JS 猜出来的路径不能直接计入 `result.json`。
3. **不声称全站覆盖。** 未访问的页面、未触发的状态变化、隐藏账号权限下的接口都可能漏掉。
4. **不解释所有私有协议。** Socket.IO、WebSocket、SSE、GraphQL 的观察和分类与“完整还原业务协议”不是一回事。
5. **不保证万能语义识别。** `auth`、`response.fields`、`note` 等可能来自观察或启发式推断，不保证和真实业务契约完全一致。
6. **不将合成测试当作官方成绩。** 不根据一个 Juice Shop 的 9 条观测记录推断所有网站的 Recall / Precision。
7. **不把脱敏等同于零泄露。** 日志/HAR/脚本缓存有一定脱敏与过滤，但真实目标文件仍可能含敏感信息；不得随意公开。
8. **不承诺操作系统级完全隔离。** 应在可信的受限 Docker/网络环境运行；是否满足组织方最终 R7/R8 限制，必须由相同配置下的系统级审计证明。

## 4. 有哪些明确的资源与探索上限？

这些是**当前源码的默认实现或专项功能上限**，不是官方强制要求，也不是每个网站都一定能达到的吞吐量：

| 项目 | 当前范围 |
|---|---|
| 运行时间预算 | CLI `--budget` 默认 **1200 秒**；可以通过命令行指定，程序可能提前因异常或阶段限制结束 |
| 请求门控 | 主流程默认最大并发 **8**，速率 **20 次请求/秒**；这是程序逻辑限制，不等于正式代理审计通过 |
| 静态爬取 | `ResourceCrawler` 默认最多 **12 个页面**、**80 份脚本记录** |
| 浏览器页面探索 | 只访问有限数量的发现页面 / 站内链接；不是无限深度爬虫；运行时导航受固定上限约束 |
| 浏览器新增 JS chunk | 最多 **32 份**、单份 **2 MiB**、合计 **8 MiB**；仅处理浏览器已下载、授权域名内的资源 |
| SSE 采样 | 默认最多 **32 KiB**、**5 秒**，只追踪第一个完整真实数据事件 |
| 显式 GET 验证 | 操作者配置的准确 URL 最多 **5 个**；默认没有就不进行该验证 |
| HAR 证据读取 | 审计器对单个 HAR 文件有 **32 MiB** 读取上限 |
| 安装与镜像 | 依赖 Python/Node/Chromium 版本与 Docker 环境；CI 构建记录不代表任意电脑也有同样性能 |

这些限制的目的，是在给定考核或练习时间里尽量提供**可复核的部分发现**，而不是无限追求覆盖率导致越界或资源失控。

## 5. 测试究竟证明了什么？

### 已经实际运行并留有记录的测试

| 证据 | 可以证明 | **不能证明** |
|---|---|---|
| [2026-11-23 主分支 CI](https://github.com/David-tiao/API/actions/runs/45139337820) | 对应提交的 **267 项 pytest**、**10 次合成 Docker/Chromium** 测试全部通过 | 世界上所有网站都能正常扫描、所有 API 都能找到 |
| [自行部署的 Juice Shop 双轮测试](https://github.com/David-tiao/API/actions/runs/45133273791) | 这两轮分别观察到 **9 条 HAR 有据的接口/传输记录**，接口集合 Jaccard **1.0000**，其中每轮 **3 条 Socket.IO 传输**被识别 | 有 9 个独立业务 REST API；Juice Shop 已被完全覆盖 |
| [SPA / Socket.IO 验收报告](ACCEPTANCE_SPA_SOCKETIO_2026-11-23.md) | 在专门的模拟路由中确实触发了后加载的 API，Socket.IO 传输类别已验证 | 一切真实 SPA、SSO 或私有 WebSocket 协议都能处理 |
| [Lazy JS 验收报告](ACCEPTANCE_RUNTIME_LAZY_CHUNKS_2026-11-23.md) | 实际加载的 JS chunk 中未执行的 API 声明不会伪装成 HAR 有据的真实 API | 这样就能自动发现所有懒加载接口 |

**重要：** Jaccard = 1.0000 是“两次输出彼此一致”，不是“真实接口准确率/召回率 100%”。

### 还没有可靠数据或正式认证的事项

- **未知站点的 Recall（召回率）和 Precision（精确率）**：缺少该站点所有真实 API 的权威清单，不能计算百分比。
- **官方 S1–S5 隐藏场景得分**：没有取得组织方正式评测结果，不应写“满分”“全部通过”。
- **正式 R7/R8 系统级验收**：现有代码与合成测试不能替代文件访问、代理、DNS、外部联网策略的等价环境审计。
- **所有机器的 Docker 性能与部署可用性**：不同宿主机、代理、权限、网络环境结果可能不同。
- **所有认证、签名、实时通信方案的完整性**：只能对已经覆盖的具体特征和对应测试作有据陈述。

## 6. 怎么判断自己应不应该用？

**适合：** 想在自己或明确授权的网页上建立“已观测 API + 请求证据”清单，检查部分前端代码线索，做开发回归，或学习前端请求是怎样发生的。

**要谨慎：** 目标需要复杂登录、多个角色、强动态签名、私有实时协议，或追求接近完整覆盖率。需要自备授权范围、测试账号、真值和人工验证。

**不适合：** 对未授权网站进行扫描；指望自动突破权限；把它当作漏洞利用器；把结果当成正式 API 文档的唯一来源；将模拟测试宣称为组织方正式得分。

### 对非技术读者的最简说明

> **我们已经做出了一个能跑、能在已测环境中发现并整理前端 API、还能给出请求证据的程序。**
>
> **我们没有做出一个能自动登录任何网站、找出所有隐藏接口、复现任何签名或保证正式考核满分的万能工具。**
>
> 这个区别就是项目真实的完成程度。
